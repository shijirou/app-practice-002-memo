# コードの読み方ガイド

AI が作ったアプリを、自分で**確認・判断・説明**できるようになるためのガイド。
コードを頭から読む必要はない。**問いを持って、決まった順に見る**。答えは、ほとんど文書とテストの名前に書いてある。

## 使い方
1. 下の「読む順」を、上から 1 つずつ行う。各ステップで「問い」に自分の言葉で答える（メモ書きでよい）。
2. 答えられない問いは、「答えのヒント」の場所を見る。それでも分からなければ、AI に聞く（聞き方は最後）。
3. 最後の「説明の練習」を、スライス（機能）ができるたびに行う。

## 地図（どこに何があるか）
| 場所 | 中身 |
|---|---|
| `docs/` | 要件・設計・画面デザイン・品質チェックの記録（**まずここ**） |
| `backend/` | API（Spring Boot）と、その自動テスト |
| `frontend/` | 画面（React）と、その自動テスト |
| `docker-compose.yml`・`.env` | DB（PostgreSQL）の起動と、接続情報（`.env` は GitHub に載せない） |

## 読む順（6 ステップ）

### ステップ 1: 何を作ると決めたか（`docs/requirements.md` の「決定事項」）
- **問い**: クライアントの要望のうち、何を決め、何を捨てたか。それぞれの理由を、1 文で言えるか。
- **ヒント**: 決定事項の表（本文だけ・新しい順・削除は元に戻せない・保存先は DB など）と、「対象外」。
- **確認**: 「もし理由を説明できない決定があれば、そこが要件の穴」。

### ステップ 2: 画面と裏側の「約束」（`docs/data-design.md`）
- **問い**: 画面は、API に何を送り、何が返るか。**失敗したとき**は、何が返り、利用者には何が見えるか。
- **ヒント**: 「API」の表と「失敗したときの返し方」の表。
- **確認**: 画面と API は別々に作られる。この約束がずれると、つながらない。

### ステップ 3: テストの名前を読む（`backend/src/test/.../MemoApiTest.java`、`frontend/src/App.test.jsx`）
- **問い**: 要件の 1 文ずつに、守っているテストはあるか。テストが無い仕様はどれか（＝確かめていない所）。
- **ヒント**: テストの名前は、**仕様の一覧**。たとえば次のように読む。
  - `本文が1001文字なら400` → 1000 文字までという決まりを守っている
  - `保存している間に打った続きの文章は、消さない` → 書いた文章を消さないという、設計の考え
- **確認**: コードが読めなくても、ここだけで「仕様が守られているか」を判断できる。

### ステップ 4: 何を保存するか（`backend/src/main/resources/db/migration/V1__create_memo.sql`）
- **問い**: 保存する項目は何か。設計書（ER 図）と、項目名・長さ・必須かどうかが合っているか。
- **ヒント**: `body VARCHAR(1000) NOT NULL`（本文は 1000 文字まで・必須）、`timestamptz`（時刻にタイムゾーンを付ける理由は `data-design.md`）。
- **確認**: 設計書と実物が食い違っていたら、まちがい。

### ステップ 5: API の中身（`backend/src/main/java/com/example/memo/`）
上から下へ、1 件の登録が流れる順に読む。
| ファイル | 役割（1 文） | 問い |
|---|---|---|
| `memo/MemoController.java` | 窓口（URL を受ける） | どの URL で、何を受け付けるか |
| `memo/MemoCreateRequest.java`・`MaxChars*.java` | 入力のチェック | 空・長すぎる本文は、どこで止まるか。空白の数え方は画面と同じか |
| `memo/MemoService.java` | 手順をまとめる | 登録と一覧は、どんな順で動くか |
| `memo/MemoRepository.java`・`Memo.java` | DB とのやりとり | 並び順は、どこで決まるか |
| `memo/MemoResponse.java` | 画面に返す形 | なぜ `Memo` をそのまま返さないのか |
| `error/GlobalExceptionHandler.java` | 失敗の形をそろえる | 失敗がどれも `{"message": "..."}` になるのはなぜか |

- **確認**: 「窓口 → 入力チェック → 手順 → DB」の流れを、自分の言葉で言えるか。

### ステップ 6: 画面の中身（`frontend/src/`）
- **問い**: 画面は、どんな「状態」を持っているか（読み込み中・保存中・失敗・一覧）。通信が失敗したとき、利用者に何が見えるか。
- **ヒント**:
  - `App.jsx`: 一覧（`memos`）と、読み込みの失敗（`loadError`）。古い読み込みが新しいものを上書きしない工夫（`latest`）
  - `MemoForm.jsx`: 入力した文章・失敗・保存中。保存に失敗しても文章を消さない所
  - `MemoCard.jsx`: 3 行までと「続きを読む」
  - `api.js`: 通信の失敗を、画面に出せる 1 文にする所
- **確認**: 「通信が切れたら？」「保存中に続きを打ったら？」の答えを、テストの名前から言えるか。

## 「良いアプリか」を判断するチェックリスト
| 観点 | 問い | 見る場所 |
|---|---|---|
| 要件に合う | クライアントの要望は、すべて満たしているか。作らないものは、理由つきで書いてあるか | `requirements.md`、画面モック |
| 使いやすい | 保存まで 3 操作以内か。迷う所・読みにくい所はないか | 実際に画面を操作する、`screen-design.md` |
| 失敗に強い | 通信が切れる・空や長すぎる入力・DB が止まる、で何が起きるか | テストの名前、`data-design.md`、起動ログ |
| 安全 | パスワードなどが GitHub に載っていないか。本物の個人情報はないか | `.gitignore`、`.env.example`、`git grep` |
| 変更しやすい | 機能を足すとき、どこを触るか分かるか。テストが守ってくれるか | フォルダの構成、テストの数 |

## 説明の練習（スライスごとに、3 問に答える）
アプリを作ったら、次の 3 つを、**自分の言葉で書く**。これが「なぜこのアプリを、この設計で作ったか」を説明する力になる。
1. **なぜ、この設計にしたか**（たとえば、なぜ保存先は DB か。ほかの案と比べて）
2. **何を捨てたか**（作らないと決めたもの。理由は何か）
3. **何が心配か**（まだ弱い所。もっと大きくなったら、どこが困るか）

答えは AI に見せて、「正しいか」「見落としはないか」を聞く。

## 分からないときの聞き方（AI に）
- 「`○○.java` の役割を、初心者向けに 3 行で。なぜこのファイルが必要か」
- 「このテストは、どの要件を守っているか。守っていない要件はあるか」
- 「この設計の代わりの案を 2 つ。それぞれの良い点と悪い点」
- 「この部分を壊すと、どのテストが失敗するか」（実際に壊して試すと、理解が深まる）
